1. Overview

org-graph-block extends org-special-block-extras with a #+begin_graph block that compiles native Org syntax — nested plain lists and two-column tables — into Graphviz dot.

No raw dot required. Nesting encodes edges; inline tables encode attributes.

1.1. Setup

(require 'org-special-block-extras)
(require 'org-graph-block)

Graphviz must be on your PATH (dot -V should work in a terminal).

1.2. Pressing C-c C-c

Anywhere inside a #+begin_graph … #+end_graph block, C-c C-c renders a PNG immediately. The output filename is auto-generated unless you supply :file: 

#+begin_graph :file my-diagram.png
…
#+end_graph

1.3. Pressing C-c ', or C-M-i

C-c ' edits the block's body in its own org-graph-edit-mode buffer. There, and in any Org buffer's graph blocks, C-M-i completes table keys and values, and eldoc explains the key at point; on the #+begin_graph line itself, they do the same for :rankdir, :node.shape, and friends. See item 3 of Quality of Life.

3. Org's Own Syntax

We want a graph block to read like the Org it is. So wherever Org already has a construct whose meaning is the graph meaning, we use it; tables remain for everything else. Each construct below is an alternative to a table row, never a replacement: <<lam>> and | :id | lam | both stay.

3.1. <<targets>> name nodes, [[links]] draw arcs

In Org, <<lam>> is a place we can link to, and [[lam]] points there. In a graph, the target is the node's id and the link is an arc to it. Moreover, C-c C-o on the link jumps to its node: 

+ <<lam>> λ-calculus
  + church
+ lisp inspired by church

lam [ label="λ-calculus" ];
lam -> church;
lisp -> lam [ label="inspired by" ];
lisp -> church;
  • Inside a graph block, Org shows links in full: we see [[lam][inspired by]], not just inspired by, since both parts matter here. Links elsewhere in the buffer keep Org's usual display.
  • The target and links vanish from the label; lisp above is labelled just lisp.
  • [[T][L]] labels the arc L; an item may have any number of links. As in Org, an item's text is its whole first paragraph, so a long line of links may wrap onto the lines below it, before its table.
  • An item that is nothing but a link, + [[church][encodes]], is a reference to the node church: its parent's arc to it is labelled encodes, and church is declared by its own item. See Edges.
  • Only links to nodes are arcs; [[https://orgmode.org][Org]] makes its node clickable, and stays Org in the label. See Web links.
  • In a #+record: table, a cell's <<target>> is its port, and its [[links]] are arcs from that port.

3.2. <<<radio targets>>> draw arcs from every mention

In Org, a radio target <<<Church>>> stays visible, and every mention of "Church" elsewhere becomes a link to it, sans brackets. In a graph, the radio target is a node, and every item mentioning it —in whatever case— has an arc to it: 

+ <<<Church>>> encodes numbers as Church numerals
+ Lisp, after Church
+ Haskell, after church and Lisp

Church [ label="Church encodes numbers as Church numerals" ];
"Lisp, after Church" -> Church;
"Haskell, after church and Lisp" -> Church;

The mention stays in the label, and the radio target's own item never arcs to itself. Mind that this is Org's semantics exactly: a casual "Church" draws an arc too.

3.3. Description lists label arcs

Org's description list, - TERM :: DEFINITION, attaches a word to an item. In a graph, that word sits on the arc into the item —read left to right, it is the arc: client, then request, then server: 

+ <<lam>> λ-calculus
+ client
  + request :: server
  + /retry/ :: server
+ Lisp
  + inspired by :: lam

lam [ label="λ-calculus" ];
client -> server [ label=request ];
client -> server [ label=<<I>retry</I>> ];
Lisp -> lam [ label="inspired by" ];
  • Two arcs between the same nodes are just two items: server above is one node, reached twice.
  • The child may be a link to a node declared elsewhere: above, inspired by's child [[lam]] arcs to λ-calculus.
  • The tag may be marked up, as /retry/ is; it is then an HTML-like label.
  • It is the terse spelling of | :edge.label | request |; an explicit :edge.label row wins.
  • A top-level item has no arc into it, so a tag there is an error.
  • As in Org, the :: needs whitespace on both sides: std::vector is a name, not a description.

3.4. Tags splice templates

On a headline, :work:urgent: classifies the entry. On an item, tags classify the node: each names a #+name: template whose rows are inherited, as an | :inherit | … | row would; explicit rows still win. Inside graph blocks, the tags wear Org's org-tag face, so they do not read as part of the label: 

#+name: wife
| color | pink |
| shape | box  |
#+name: faint
| style | dotted |

+ Khadija :wife:faint:
  | color | red |

Khadija [ shape=box style=dotted color=red label=Khadija ];

Tags are trailing :word: groups, exactly as on a headline. So colons anywhere else are just text, and a node label that needs a trailing :word: of its own puts it in =verbatim=, or in a | label | row: 

+ Ratio 1:2
+ std::vector
+ Meeting at 12:30 :faint:
+ Vim's =:wq:=

"Ratio 1:2" [ label="Ratio 1:2" ];
"std::vector" [ label="std::vector" ];
"Meeting at 12:30" [ style=dotted label="Meeting at 12:30" ];
"Vim's :wq:" [ label=<Vim's <FONT FACE="monospace">:wq:</FONT>> ];

A tag naming no template is an error, rather than a typo silently becoming part of the label. While prototyping, though, we want shapes before names: #+begin_graph :unknown-tags random-templates makes up a template for each unknown tag —a colour, a shape, a font— the same at every use, so the tags read at a glance. A legend entry gives each its meaning; when the design settles, #+name: tables replace the made-up templates, one tag at a time:

The Nth unknown tag takes the Nth of org-graph-random-template-colours, -shapes, and -fonts, so renders are stable, and the first eight tags differ in every way.

3.5. Subtrees inherit #+node:, #+edge:, and #+rank:

Org's properties are inherited: a :PROPERTIES: drawer on a heading reaches its subheadings. So it is with an item's #+node: and #+edge: tables: they style every node and arc beneath the item, while the item itself keeps its own | key | value | rows; its #+rank: lines apply there too. Graphviz scopes such defaults by an anonymous subgraph, which draws no box: 

+ Weather
  #+node:
  | shape | box |
  #+edge:
  | style | dotted |
  + Rain
    + Umbrella
  + Sun
+ Climate

Weather [ label=Weather ];
subgraph {
  node [ shape=box ]
  edge [ style=dotted ]
  Weather -> Rain;
  Rain [ label=Rain ];
  Rain -> Umbrella;
  Umbrella [ label=Umbrella ];
  Weather -> Sun;
  Sun [ label=Sun ];
}
Climate [ label=Climate ];

A deeper item's tables override a shallower one's, as nested :PROPERTIES: do; a node first declared elsewhere keeps the defaults of where it was declared.

3.6. Legends are description lists

A legend says what each style means: a glossary of templates. Org's glossary is the description list, so a top-level - :T: :: MEANING —which has no parent to arc from— is a legend entry: a sample styled by template T, captioned MEANING. Wrap the entries in a #+begin_cluster to box them: 

#+name: married
| color | pink |
| dir   | both |
#+name: wife
| shape | box |

+ Muhammad
+ Khadija :wife:
  + Muhammad :married:
#+begin_cluster Legend
- :married: :: marriage
- :wife: :: /wife/
#+end_cluster

subgraph cluster_Legend {
  label=Legend
  legend_1 [ shape=point style=invis ];
  legend_1_end [ shape=point style=invis ];
  legend_1 -> legend_1_end [ color=pink dir=both label=marriage ];
  legend_2 [ shape=box label=<<I>wife</I>> ];
}
  • A template that styles some arc in the graph —by a reference's or a term's tags, an :edge.:inherit row, or an #+edge: line— is sampled as an arc; any other, as a node.
  • …~, sample their templates together.
  • The sample drops constraint, which shapes the layout rather than the arc.
  • The legend can never drift from the graph: change married, and its sample changes too.

3.7. Footnotes are tooltips

A footnote is an aside we read when we want it; so is a tooltip. An inline footnote leaves the label and becomes the node's tooltip —shown on hover in an :svg t HTML export: 

+ Lisp [fn::McCarthy, 1958]

Lisp [ tooltip="McCarthy, 1958" label=Lisp ];

A named footnote serves too: [fn:NAME: NOTE] inline, or a bare [fn:NAME] whose [fn:NAME] NOTE definition sits elsewhere in the buffer —say, below the graph. An explicit | tooltip | … | row wins.

3.8. Notes are longer tooltips, or shown in the node

A footnote is awkward for more than a line. An item's text is its first paragraph, as in Org; every paragraph after it is a note, the tooltip of whatever its item's line describes: a node, or —under a reference— an arc. #+begin_note :edge, sitting in an item as a #+begin_cluster may, describes the arc into the item instead; it is the one place we need the block: 

+ Lisp [fn::1958]

  McCarthy's /list processor/:
  code is data.
  + Scheme
    #+begin_note :edge
    Steele and Sussman distilled it.
    #+end_note

Lisp [ tooltip="1958\nMcCarthy's list processor: code is data." label=Lisp ];
Lisp -> Scheme [ tooltip="Steele and Sussman distilled it." ];

The blank line matters: without it, McCarthy's list processor: continues the first paragraph, and so the label. Likewise + <<lisp>> Lisp, the list processor names its node lisp and labels it with the whole line; a <<target>> names, but only a new paragraph begins a note.

Tooltips need a hover, and an exported PNG has none. #+begin_graph :notes inline shows every note beneath its label instead, in a smaller font, its markup kept and its lines filled to :wrap —else 40— characters:

  • A note's lines join, and each paragraph —or \\ break— starts a new line.
  • A note follows the item's footnotes, which stay tooltips; an explicit tooltip, :edge.tooltip, or label row wins.
  • A note outside every item is the graph's: its tooltip, or —inline— the text beneath its title. One directly in a #+begin_cluster is the box's.
  • Within a graph, #+begin_note is never the callout of the same name, and C-c C-c in it renders the graph.

3.9. Markup makes rich labels

*bold*, /italic/, _underline_, +strike+, =code=, and ~pre~ in an item's text make its label an HTML-like one, while its id stays the plain text: 

+ *Church* encodes =Bool=

"Church encodes Bool" [ label=<<B>Church</B> encodes <FONT FACE="monospace">Bool</FONT>> ];

We escape &, <, >, and " for you. Graphviz has no way to tell =code= from ~pre~, so both are monospace. A #+record: table's cells keep their markup too. Names such as a_b, C++, and org-graph.el are not mistaken for markup.

Org's entities are their characters, and braced sub- and superscripts are Graphviz's own; as under Org's #+options: ^:{}, an unbraced a_b stays text, so snake_case ids are safe. A @@dot:…@@ export snippet is raw label HTML, for whatever Org has no markup for; a snippet for any other backend vanishes: 

+ \alpha \to \beta
+ x^{2} H_{2}O
+ @@dot:<FONT COLOR="red">@@Alert@@dot:</FONT>@@

"α → β" [ label="α → β" ];
"x2 H2O" [ label=<x<SUP>2</SUP> H<SUB>2</SUB>O> ];
Alert [ label=<<FONT COLOR="red">Alert</FONT>> ];

Timestamps, statistics cookies, and citations show as written; LaTeX fragments too, since Graphviz has no math. Syntax that means nothing in a graph —a headline, a #+begin_quote, an unknown #+key:— is an error, rather than silently dropped; comments are fine.

3.10. \\ breaks a line

In Org, a \\ ending a line is a hard line break; in a graph, it breaks the node's label. Since a label seldom wants a literal \\, it may sit mid-line too, so a two-line node stays one terse line: 

+ Emacs
  + provides :: <<closures>> Closures \\ (lexical scope)
  + *Lisp* \\
    McCarthy, 1958

Emacs -> closures [ label=provides ];
closures [ label=<Closures<BR/>(lexical scope)> ];
Emacs -> "Lisp McCarthy, 1958";
"Lisp McCarthy, 1958" [ label=<<B>Lisp</B><BR/>McCarthy, 1958> ];

The label becomes an HTML-like one, as with markup; the id joins the lines with a space, so a node reached by a link usually wants a <<target>>, as closures above.

It is the one line break wherever a label is written: a description term, a table value, a #+record: cell. So an arc's label breaks just as its node's does: 

+ Monad
  + every monad \\ is an adjunction :: Adjunction
  + Turing
    | :edge.label | Church– \\ Turing thesis |

Monad -> Adjunction [ label=<every monad<BR/>is an adjunction> ];
Monad -> Turing [ label="Church–\nTuring thesis" ];

3.11. Web links are URLs, image links are images

A link to anything but a node keeps its Org meaning. A web or file link makes the node clickable in an :svg t HTML export, its description staying in the label; a description-less link to an image draws that image: 

+ Org mode
+ <<emacs>> Emacs file:emacs.png
+ file:gnu.png

"Org mode" [ URL="https://orgmode.org" label="Org mode" ];
emacs [ image="emacs.png" label=Emacs ];
"gnu.png" [ image="gnu.png" label="" ];

A node has one URL, so an item with two web links is an error. Graphviz finds the image relative to the Org file, as Org does; an explicit URL or image row wins.

So a graph of screenshots is a tour. A lone image is its own node, drawn sans text, so the arc into it carries the words; imagescale fits each picture to its node's fixed size:

A link to a section, [[*Heading]], is a URL too —not an arc, since nodes are named without a star. In an :svg t HTML export it leads to that section's anchor, which only Org knows; and in Emacs, a click on the rendered node opens the section. So a graph may be a map of its own document: 

#+begin_graph Org's own syntax :svg t :rankdir LR
+ [[*Org's Own Syntax][Syntax]]
  + [[*Footnotes are tooltips][Footnotes]]
  + [[*Notes are longer tooltips, or shown in the node][Notes]]
#+end_graph

A bare [[*Footnotes are tooltips]] labels its node with the heading's title; [[#custom-id]] and [[id:…]] links work alike.

3.12. Checkboxes are templates

A checkbox says how far along a thing is; so a graph of tasks is just a checklist. [X], [-], and [ ] apply the templates checked, partial, and unchecked, as a :checked: tag would; and C-c C-c on a checkbox toggles it, as Org's own does, then renders the graph: 

#+name: unchecked
| style | dashed |

+ [-] compile
  + [X] parse
  + [ ] typecheck

compile [ color=darkorange fontcolor=darkorange label=compile ];
parse [ color=forestgreen fontcolor=forestgreen label=parse ];
typecheck [ style=dashed label=typecheck ];

checked and partial default to green and orange, by org-graph-checkbox-templates; a graph's own #+name: template wins. A checkbox whose template exists nowhere, such as unchecked by default, styles nothing.

3.13. Macros name values

A palette repeats itself. Org's #+macro: names a value once, and {{{name}}} uses it —in a table, an item, anywhere in the block: 

#+macro: gold #f9e2af
#+begin_graph
+ Church
  + Turing
    | :edge.color     | {{{gold}}} |
    | :edge.fontcolor | {{{gold}}} |
#+end_graph

Templates name whole bundles of rows; macros name single values. An undefined macro is an error.

In similar spirit, inline src_LANG{…} blocks and call_NAME() calls run at export, as anywhere in Org, their results landing in the label; C-c C-c shows them as written.

3.14. Ordered lists keep their order

+ - * say “these things”; 1. 2. 3. say “first, second, third”. So ordered children sit side by side, on one rank, in the order written —Graphviz no longer reshuffles them to save a crossing: 

+ λ-calculus
  1. Church
  2. Turing
  3. Kleene

"λ-calculus" [ ordering=out label="λ-calculus" ];
"λ-calculus" -> Church;
"λ-calculus" -> Turing;
"λ-calculus" -> Kleene;
{ rank=same; Church; Turing; Kleene }

An ordered top-level list, or one inside a cluster, shares a rank too. An explicit | :children-rank | min | wins over the rank=same; a lone ordered child gets no rank at all. For same rank without the fixed order, use | :children-rank | same | with + bullets.

Nodes with no common parent share a rank by #+rank:, which takes bare ids or links; a link spares a multi-word id its quotes: 

+ Logic
  + λ calculus
+ Lisp
#+rank: Lisp [[λ calculus]]

{ rank=same; "λ calculus"; Lisp }

Under splines=curved, Graphviz drops the label of an arc between two nodes on one rank; so there, such an arc's label becomes an xlabel, which it still draws.

3.15. The #+begin_graph line

The header line takes the graph's title and any graph attribute, so small graphs need no preamble: 

#+begin_graph Lambda calculus :rankdir LR :node.shape box :edge.color grey
+ λ
  + Lisp
#+end_graph

graph [ label="Lambda calculus" rankdir=LR ]
node [ shape=box ]
edge [ color=grey ]
  • The title, the words before the first :key, is the graph's label; :directed nil makes the graph undirected.
  • :KEY V is a graph attribute; :node.KEY V and :edge.KEY V are node and edge defaults —the same KEY, node.KEY, edge.KEY spelling as table rows.
  • :wrap N fills node and arc labels to lines of N characters, so long item text needs no \\ breaks; a label already broken by \\ stays as written.
  • :notes inline shows notes beneath labels rather than as tooltips; :unknown-tags random-templates makes up templates for unknown tags; :unflatten N staggers wide rows of leaves.
  • :file, :svg, :directed, :wrap, :notes, :unflatten, :unknown-tags, and :C-c_C-c belong to the block itself, never to Graphviz; so do the Babel habits :exports and :results, which the block ignores.
  • The block's own #+graph:, #+node:, and #+edge: tables override the header.
  • As on Org's own #+attr_html: lines, values need no quotes: :bgcolor #6c7086, :fontname Helvetica,Arial. A value with spaces does: :fontname "Helvetica Neue".
  • When the preamble outgrows the line, a drawer of any name ---:SETTINGS:, :PALETTE:— folds its #+graph:, #+node:, #+edge:, #+rank:, and #+name: lines away with TAB.

3.19. Decision trees

A decision tree is a tree whose nodes come in kinds: decisions we make (boxes), chances we take (circles), and outcomes (bare text), with each chance's arcs labelled by how likely it is. Templates name the kinds, description terms label the arcs, and an item's #+edge: dashes every arc of chance beneath it:

The chance node is all target: <<specials>> names it, and its template's empty label leaves a dot.

3.20. Smart diagrams: :smartdiagram TYPE

Graphviz lays out a graph; LaTeX's smartdiagram package typesets a handful of fixed pictures —a planet amid its satellites, a flow of boxes, a column of terms and their descriptions— that suit a README's opening better than any graph. :smartdiagram TYPE hands the very same list to smartdiagram instead; C-c C-c renders it with pdflatex, and LaTeX export typesets it in place:

  • TYPE is one of constellation, connected-constellation, bubble, flow, flow:horizontal, circular, circular:clockwise, descriptive, priority-descriptive, or sequence.
  • A constellation or bubble has one top item, its centre; that item's children orbit it. A descriptive diagram's items are + TERM :: DESCRIPTION. Every other type reads the top items, in order.
  • The #+graph: rows are \smartdiagramset's, in smartdiagram's own words: | planet color | black!75 |.
  • An item's | color |, | fontcolor |, and | fontsize | rows —Graphviz's names for them— colour its shape and its text, and size its text; its :tags: splice #+name: templates of those rows, as in any graph. An item's later paragraphs sit beneath its text.
  • The title sits above the diagram; prose before the list, between the two; prose after it, beneath.
  • :dpi N sets the PNG's resolution, 300 by default. C-u C-c C-c shows the LaTeX.
  • C-M-i and eldoc know which kind of graph they are in: under :smartdiagram, they offer smartdiagram's keys, with their defaults, rather than Graphviz's.
  • Graphviz's own syntax ---#+node:, #+edge:, #+rank:, links between items, records— draws nothing here, so it is an error rather than silently dropped.

3.20.1. Org's markup in place of LaTeX's

The diagram above began life as a #+begin_src latex-as-png block, via ob-latex-as-png. Every LaTeX incantation it needed has an Org counterpart that we already write daily:

LaTeX Org
\smartdiagram[constellation diagram]{…} :smartdiagram constellation, over a nested list
\smartdiagramset{planet color=black!75, …} a #+graph: table, one row a key
\newcommand{\old}[1]{\textcolor{black!70}{\texttt{#1}}} #+macro: old [[color:gray][=$1=]]
\texttt{(:k plist)}, \textbf{…} =(:k plist)=, *…*

3.21. #+name: and #+caption: make a figure

In Org, #+name: is what [[links]] reach, and #+caption: captions a table or an image. A graph is an image, so both mean what they always do: 

As lineage shows, Emacs is a Lisp.

#+name: lineage
#+caption: How Emacs came to be
#+begin_graph
+ λ-calculus
  + Lisp
    + Emacs Lisp
#+end_graph
  • The graph renders to lineage.png —both on C-c C-c and on export— and exports as that image, numbered and captioned: [[lineage]] reads “Figure 1” in HTML, and \ref in LaTeX.
  • An explicit :file still wins: #+begin_graph :file elsewhere.png renders there, and the #+name: still labels it. With :svg t, the figure is lineage.svg.
  • An unnamed graph exports as before: inlined into HTML, or as dot source elsewhere.

3.22. Sections are graphs: the :graph: tag

A #+begin_graph block is a function on a region; a :graph: tag is the same function on a section. The section's text is the graph, and its :PROPERTIES: drawer —Org's own home for key-value settings— is the #+begin_graph line: :RANKDIR: LR is :rankdir LR, :NODE.SHAPE: box is :node.shape box, and :FILE: is :file. See the live example: 

* Emacs's lineage :graph:
:PROPERTIES:
:RANKDIR: LR
:NODE.SHAPE: box
:END:
+ λ-calculus
  + inspired :: Lisp
    + Emacs Lisp
  • The heading stays a heading; only its text becomes the graph, on export.
  • :graph_Some_Title: titles the graph Some Title, as the words before the first :key would.
  • Org's own properties, such as :CUSTOM_ID: and :CATEGORY:, stay Org's; they never reach Graphviz.

4. Keys, Edges, Records, and Ports

4.1. Ids and labels

Every node has an id, which arcs and links name, and a label, which is drawn. By default both are the item's text; so these three items, spelling it out more and more, all declare one and the same node: 

+ Lisp

+ <<Lisp>> Lisp

+ Lisp
  | :id   | Lisp |
  | label | Lisp |

Lisp [ label=Lisp ];

When the two should differ, we set either one apart: a <<target>> or an | :id | row gives the id, and a | label | row gives the label: 

+ <<lam>> λ-calculus
+ Combinatory Logic
  | :id | combinatory |
+ Church
  | label | Alonzo Church |

lam [ label="λ-calculus" ];
combinatory [ label="Combinatory Logic" ];
Church [ label="Alonzo Church" ];
  • The id is the :id row, else the <<target>>, else the text —sans markup, links, footnotes, and tags.
  • The label is the label row, else the text; markup makes it an HTML-like one.
  • Two items with one id are one node, so an item may appear twice to gain more children.

4.2. Two kinds of keys

By way of example, this item has one row of each kind: 

+ Alonzo
  | label | Alonzo Church |
  | :id   | church        |

church [ label="Alonzo Church" ];

A plain key, such as label, is a Graphviz attribute of the node, passed straight through. We quote its value for you, so Alonzo Church, #00ff00, and x -> y all need no quotes; already-quoted values, and <…> HTML labels, are left alone.

A key starting with a colon is reserved: it means something to the graph block itself, never to Graphviz. A leading colon is never a Graphviz attribute, so the two kinds cannot clash. The reserved keys are listed in org-graph-reserved-keys:

Key Meaning
:id the node's name for cross-references; else its <<target>>, else its text
:edge.KEY attribute KEY of the arc from the parent
:edge[T].KEY attribute KEY of this item's arc to T
:inherit inherit the rows of #+name: templates; also :NAME: tags
:children-rank { rank=… } over this item's immediate children

An unknown :key is an error rather than a silently ignored attribute.

4.3. Edges: nesting, :edge.KEY, and links

Nesting makes an arc from parent to child; :edge.KEY rows on the child style that arc. Every attribute is its own row, exactly like a node's, so there is one key-value syntax throughout. For a mere label, the description list + request :: server is terser; see Description lists label arcs. A parallel arc is simply a second child, styled on its own; a KEY given twice is an error: 

+ client
  + request :: server
    | :edge.color | blue |
  + retry :: server
    | :edge.style | dashed |

client -> server [ label=request color=blue ];
client -> server [ label=retry style=dashed ];

Arcs that nesting cannot express —to a node declared elsewhere— are links. A child item that is nothing but a link is a reference to its target; nesting makes the arc, and the child's :edge.KEY rows style it, exactly as for any other child. So each arc is its own small paragraph: 

+ <<lam>> λ-calculus
+ Fortran
+ Lisp
  + borrows :: lam
    | :edge.style | dotted |
  + Fortran

Lisp -> lam [ label=borrows style=dotted ];
Lisp -> Fortran;
  • A reference never declares its target: the target's own item names and labels it, even when that item comes later. Node attributes on a reference are an error; they belong on the target's item.
  • Two references to one target are two parallel arcs, each styled on its own.
  • A reference may name a record's port, [[struct1::mid]], or a cluster.

For a quick arc, a link may also sit in the item's own text; once the arc wants styling, it graduates to a reference child: 

+ <<lam>> λ-calculus
+ Fortran
+ Lisp borrows Fortran

Lisp -> lam [ label=borrows ];
Lisp -> Fortran;

As in Org, an item's tables and directives may also follow its sub-items; they still belong to it.

4.4. Templates: #+name:, :tags:, and :inherit

A family tree repeats itself: every marriage is the same pink, two-headed arc, and every wife the same boxed node. Rather than restate those rows each time, we name them once. A #+name: table is a reusable bundle of rows, and a tag applies it to whatever its line describes —after an item, its node; after a reference, its arc: 

#+name: married
| color | "#cc3399" |
| dir   | both      |
#+name: wife
| shape | box |

+ Muhammad
+ Khadija :wife:
  + Muhammad :married:
    | :edge.color | red |

Muhammad [ label=Muhammad ];
Khadija [ shape=box label=Khadija ];
Khadija -> Muhammad [ dir=both color=red ];

Explicit rows win over a template's, so the marriage above is red. A line may carry several tags, :married:faint:, each a template. The same rule reaches every other line a template could apply to:

Line What its tags style
+ Khadija :wife: the node
+ [[Muhammad]] :married: the arc to the reference
+ wed :married: :: Khadija :wife: the arc, by the description term's tags; the node, by its own
#+node: :wife: every node; likewise #+edge: and #+graph:
#+name: wife :base1:base2: the template wife, which inherits base1 and base2

Each tag is terse sugar for an :inherit row, which names one or more templates and is often the clearer choice in a long-lived graph: | :inherit | wife | in an item's table or under #+node:, | :edge.:inherit | married | for the arc into an item. Wherever it sits, the item's explicit rows still win.

A template may inherit others; one that, directly or not, inherits itself contributes nothing the second time. A name that no #+name: defines is an error, rather than a silent nothing.

As with Babel's named tables, a #+name: table anywhere in the buffer, outside any graph, is a template every graph in the buffer may use; so a house style ---wife, married— is named once per file rather than once per graph. A graph's own template of the same name wins, and a template inside one graph stays that graph's own.

4.5. Records: a #+record: table

A record is a node drawn as a table, and Org already has tables: under #+record:, an item's table is its label, laid out exactly as written —just as #+graph:, #+node:, and #+edge: name what the table below them is. A cell's <<target>> is its port, a cell's [[link]] is an arc from that port, and an arc reaches a port by record::port —just as Org's [[file:notes.org::target]] reaches into a file: 

+ struct1
  #+record:
  | left | <<mid>> middle struct2::one | right |
+ struct2
  #+record:
  | <<one>> one | two   |
  | ^           | three |
+ reader
  + struct1::mid

struct1 [ shape=plain label=<<TABLE …><TR><TD>left</TD><TD PORT="mid">middle</TD><TD>right</TD></TR></TABLE>> ];
struct1:mid -> struct2:one;
struct2 [ shape=plain label=<<TABLE …><TR><TD PORT="one" ROWSPAN="2">one</TD><TD>two</TD></TR><TR><TD>three</TD></TR></TABLE>> ];
reader -> struct1:mid;

Org tables have no merged cells, so two markers stand in for them: ^ continues the cell above, as one does, and an empty cell continues the cell to its left —or, in the first column, the one above. Together they draw any layout that Graphviz's old { } nesting could: 

+ struct3
  #+record:
  | hello \\ world | b |            |   | g | h |
  | ^              | c | <<here>> d | e | ^ | ^ |
  | ^              | f |            |   | ^ | ^ |

Here b and f span three columns, hello, g, and h three rows; a \\ breaks a line, as in an item.

Hlines and column cookies mean what they mean to Org. An hline draws a rule between rows, and a table with any hline draws one outer border rather than a box around every cell —so a UML class is just the table we would write anyway. A row of <l>, <c>, and <r> cookies aligns its columns, and cells keep their markup: 

+ Person
  #+record:
  | <l>            |
  | *Person*       |
  |----------------|
  | name: =String= |
  | age: =Int=     |
  |----------------|
  | greet()        |

Person [ shape=plain label=<<TABLE BORDER="1" CELLBORDER="0" CELLSPACING="0"><TR><TD ALIGN="LEFT" BALIGN="LEFT"><B>Person</B></TD></TR><HR/>…</TABLE>> ];
  • A record is otherwise an ordinary node: its children are nodes of their own, and its attributes, tags, and templates apply as usual; color, fillcolor, and fontcolor colour the table. Its attribute table goes above #+record:, since rows right below the record table are part of it.
  • A record is shape=plain, the table being its whole outline; an explicit shape row wins.
  • A cell with a link but no target is ported by its text, spaces as underscores; <<x marks the spot>> is likewise reached as [[struct3::x marks the spot]].
  • Ports belong to their record, so two records may both have a head port: r1::head and r2::head.
  • A cell's trailing tags style its arcs, as a reference's style its arc: | <<mid>> middle [[struct2::one]] :dashed: | draws a dashed arc. A cell with tags but no link is an error; write =:x:= for literal text.
  • a::b names a port only when a names a record; otherwise it is an ordinary node, such as std::vector. Record and port names may contain dots: [[org.el::v1.2]].
  • Graphviz spells ports record:port; that is the spelling in the generated dot.

4.6. Clusters

A cluster is a box drawn around some nodes: a subgraph, so it gets the graph's own spelling. A #+begin_cluster block takes a title and :KEY V attributes, :node.KEY and :edge.KEY defaults included, exactly as the #+begin_graph line does; and, being a block, it folds with TAB: 

+ Emacs
  #+begin_cluster Packages :bgcolor lightgrey :node.shape box
  + Org
    #+begin_cluster
    + agenda
    + babel
    #+end_cluster
  + Magit
  #+end_cluster

graph [ compound=true ]
subgraph cluster_Packages {
  label=Packages
  bgcolor=lightgrey
  node [ shape=box ]
  Org [ label=Org ];
  subgraph cluster_anonymous_1 { label="" agenda; babel; }
  Org -> agenda [ lhead=cluster_anonymous_1 ];
  Magit [ label=Magit ];
}
Emacs -> Org [ lhead=cluster_Packages ];
  • A cluster block inside an item is that item's child: above, Emacs has an arc to Packages.
  • An untitled cluster is an anonymous box, with no label and no name to draw arcs to.

  • When the attributes outgrow the line, a table opening the block styles the box, as an item's table styles its node; #+node: and #+edge: tables set defaults inside it, as usual: 

    #+begin_cluster Prophets
| style     | filled  |
| fillcolor | #ddeeff |
#+node:
| fillcolor | #aaccff |
+ Adam
#+end_cluster
  • The title runs up to the first :KEY; #+begin_cluster Time 12:30 is titled Time 12:30.
  • C-c C-c, C-M-i, and eldoc work inside a cluster block just as anywhere else in the graph.

An arc to or from a cluster lands on the cluster's first node, clipped at its border, as lhead shows above.

4.7. Strictly tables: :edge[T].KEY and | shape | cluster |

Some of us prefer every attribute in a key-value table, never in the list's shape. Two spellings serve that taste; the examples above avoid them, but they are fully supported.

An inline link's arc is styled by :edge[T].KEY, naming the arc by where it goes; :edge[T].:inherit applies a template to it. A row with no [[T]] link in the item's text is an error: 

+ <<lam>> λ-calculus
+ Lisp borrows
  | :edge[lam].style | dotted |

Lisp -> lam [ label=borrows style=dotted ];

A | shape | cluster | row makes an item a cluster, as #+begin_cluster does. Its children are then its members rather than arc targets, so arcs out of them are inline links, styled as above: 

+ Emacs
  + Packages
    | shape | cluster |
    + Org
    + Magit

graph [ compound=true ]
subgraph cluster_Packages { label=Packages Org; Magit; }
Emacs -> Org [ lhead=cluster_Packages ];

6. Quality of Life

  1. Pressing C-u C-c C-c inside a #+begin_graph block shows the generated Graphviz dot source in a *org-graph dot* buffer instead of rendering a PNG. A #+RESULTS: block containing a fenced #+begin_src dot … #+end_src is inserted (or replaced) in the org file so the source is preserved.

    For blocks where you always want dot output, add :C-c_C-c dot to the header: 

    #+begin_graph :C-c_C-c dot
…
#+end_graph

    Plain C-c C-c on such a block shows dot; C-u C-c C-c toggles back to PNG. The two controls compose via XOR — prefix always flips whatever the block default is.

  2. Pressing C-u RET on any table row inside a #+begin_graph block inserts a new | key | value | row interactively — a completion menu for the key, then one for the value (or a free-text prompt when the attribute accepts arbitrary strings).

    The menu is context-aware: it shows only attributes valid for the structural location of the table:

    • Table under #+graph: → graph-level attributes (rankdir, splines, bgcolor, …)
    • Table under #+node: → default node attributes (shape, style, color, …)
    • Table under #+edge: → default edge attributes (arrowhead, dir, penwidth, …)
    • Table on a list item → node attributes (same as above)

    The full attribute catalogue lives in the org-graph-attributes defcustom, in org-graph-attributes.el (customise via M-x customize-variable RET org-graph-attributes); each entry has the form: 

    (:name "shape" :valid-on (nodes) :default "ellipse"
 :values ("box" "polygon" "ellipse" …)  ;; nil → free-text prompt
 :description "Sets the shape of a node.")

    For a colour ---bgcolor, fillcolor, fontcolor, or color— the value is picked from Helm's colour list, when Helm is installed; RET inserts the colour's hex code, and its name as a comment.

    Plain RET is unaffected — only the prefixed C-u RET triggers the completion.

  3. C-M-i (completion-at-point) and eldoc know about graph keys —in any Org buffer's graph blocks, and in the org-graph-edit-mode buffer that C-c ' opens on one:

    • In a key cell, completion offers the attributes valid there, plus the reserved keys; after :edge. or :edge[T]., it offers only edge attributes, prefix and all. In a value cell, it offers the values of that row's attribute, such as vee for :edge.arrowhead. Each candidate is annotated with its description.
    • On the #+begin_graph line, :r C-M-i offers :rankdir and the other graph attributes, every :node.KEY and :edge.KEY, and the block's own :file, :svg, :directed, and :C-c_C-c; :rankdir L C-M-i then offers LR.
    • Eldoc shows the description of the key on the current row, or at point on the #+begin_graph line, ending with Graphviz's default; e.g., | :edge.arrowhead | vee | shows “Style of arrowhead on the head node of an edge. Default: normal.”
    • C-u RET works in the C-c ' buffer too.

    The descriptions come from org-graph-attributes, which lives on its own in org-graph-attributes.el: every Graphviz attribute, scraped from Graphviz's attribute table. To add or adjust an attribute, edit its entry there, or M-x customize-variable RET org-graph-attributes. Reserved keys are described by org-graph--reserved-key-docs, and the header's own keys by org-graph--header-key-docs.

  4. The image C-c C-c renders is clickable. Hovering over a node or cluster shows its tooltip —its footnotes and notes— and a click follows it: to its link's target, when its item has a web, file, or [[*Heading]] link; else to the item itself, in the #+begin_graph block. Graphviz writes an image map (-Tcmapx) beside the PNG, from the same layout, and its areas become the image's :map; it is scaled as the image is, say by org-image-actual-width.

    The map lives only as long as the image does: an image Org redisplays itself, say on reopening the file, is clickable again after another C-c C-c.
