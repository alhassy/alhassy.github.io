1. An outline is already a graph

Say we are showing a friend how 1 * 2 + 3 - 4 parses. On paper, we would draw a tree. In Org, we would reach for Graphviz —and write that tree a second time, in a second language: 

digraph { "-" -> "+"; "-" -> 4; "+" -> "*"; "+" -> 3; "*" -> 1; "*" -> 2; }

Every arc there restates what an outline's indentation already says. So we write the outline, and let the outline be the graph. Each demo in this README shows what we write, then what we get:

﴾What You Write﴿ 
#+begin_graph
+ -
  + +
    + *
      + 1
      + 2
    + 3
  + 4
#+end_graph
﴾What You Get﴿

That is the whole idea. A #+begin_graph block compiles the Org we already write —nested lists, two-column tables, links, tags, footnotes— into Graphviz dot. Nesting is an arc; the rest of this README refines that one sentence, one gap at a time, and every example stays with our running theme: parsing 1 * 2 + 3 - 4, from characters to tokens to trees.

A wide graph shrinks to fit the page; a click on it shows it full size, and another shrinks it back. LaTeX export draws it too, as a vector PDF by dot, shrunk likewise to fit the line.

1.1. Setup

org-graph-block extends org-special-block-extras: 

(require 'org-special-block-extras)
(require 'org-graph-block)

Graphviz must be on our PATH: dot -V should work in a terminal.

1.2. A REPL for pictures

The fun part is how quickly a picture grows. Start with the seven tokens as a flat list, one item each, and press C-c C-c anywhere in the block: seven lonely nodes.

﴾What You Write﴿ 
#+begin_graph
+ 1
+ *
+ 2
+ +
+ 3
+ -
+ 4
#+end_graph
﴾What You Get﴿

Now M-S-<right> demotes an item, children and all —Org's own list editing— and another C-c C-c shows the new arc. A minute later, the flat list is the tree above. (Plain M-<right> demotes the item alone, leaving its children behind, as anywhere in Org.)

C-c C-c renders a PNG and links it beneath the block, under #+RESULTS:. The file's name is made up, unless :file picks one, as in #+begin_graph :file parse-tree.png. When the picture surprises us, C-u C-c C-c shows the generated dot instead; see Comforts while editing.

2. Arcs that speak: description lists

A bare arc says “related”, and little else. Explaining how our expression becomes a value, we want each arc to say how: the source text is lexed into tokens, which are parsed into a tree. Org's description list, - TERM :: DEFINITION, already attaches a word to an item; in a graph, that word sits on the arc into the item. Read left to right, the line is the arc —source, then lexed into, then tokens:

﴾What You Write﴿ 
#+begin_graph :direction right
+ ="1 * 2 + 3 - 4"=
  + lexed into :: tokens
    + parsed into :: syntax tree
      + evaluated to :: -1
      + compiled to :: bytecode
#+end_graph
﴾What You Get﴿

Two arcs between the same nodes are just two items. A parser both consumes its tokens and peeks at the next one, unconsumed; two arcs, one stream:

﴾What You Write﴿ 
#+begin_graph :direction right
+ parser
  + consumes :: token stream
  + /peeks at/ :: token stream
#+end_graph
﴾What You Get﴿
  • The term may be marked up, as /peeks at/ is; it is then an HTML-like label.
  • It is the terse spelling of | :edge.label | consumes |, met below; an explicit :edge.label row wins.
  • A top-level item has no arc into it, so a term there is an error —except for a legend entry, met later.
  • As in Org, the :: needs whitespace on both sides: std::vector is a name, not a description, and so is BNF's expr ::= term, as ::= is not ::.

3. Arcs that leave the tree: targets and links

A tree gives each node one parent; grammars are not so tidy. An expr is made of term's, a term of factor's, and a factor is a number —or a whole expr again, in parentheses. That last arc goes back up the tree, so it must reach a node declared elsewhere. Org already names places and points at them: <<expr>> is a place we can link to, and [[expr]] points there. In a graph, the target is the node's id, and the link is an arc to it. Moreover, C-c C-o on the link jumps to its node:

﴾What You Write﴿ 
#+begin_graph
+ <<expr>> expression
  + term
    + factor [[expr][( … )]]
      + number
#+end_graph
﴾What You Get﴿
  • The target and links vanish from the label; factor above is labelled just factor.
  • [[T][L]] labels the arc L; an item may have any number of links. As in Org, an item's text is its whole first paragraph, so a long line of links may wrap onto the lines below it, before its table.
  • Inside a graph block, Org shows links in full: we see [[expr][( … )]], not just ( … ), since both parts matter here. Links elsewhere in the buffer keep Org's usual display.
  • Only links to nodes are arcs; [[https://orgmode.org][Org]] makes its node clickable, and stays Org in the label. See Web links.

3.1. A child that is just a link: references

An inline link is quick, but its arc has nowhere to keep a style of its own. So the arc graduates to a child item that is nothing but a link: a reference to its target. Nesting makes the arc, and a description term labels it, exactly as for any other child:

﴾What You Write﴿ 
#+begin_graph
+ <<expr>> expression
  + term
    + factor
      + number
      + in parentheses :: [[expr]]
#+end_graph
﴾What You Get﴿
  • A reference never declares its target: the target's own item names and labels it, even when that item comes later. Node attributes on a reference are an error; they belong on the target's item.
  • + [[expr][in parentheses]] is a reference too, its arc labelled in parentheses; tags ending the description style the arc, + [[expr][in parentheses :dashed:]], and alone leave it unlabelled, + [[expr][:dashed:]]. Tags after a reference are an error, since its node is declared elsewhere.
  • Two references to one target are two parallel arcs, each styled on its own.
  • A reference may name a record's port, [[node::left]], or a container; both are met below.

3.2. Radio targets: arcs from every mention

When one node is mentioned everywhere, bracketing each mention is a chore. A grammar mentions its tokens in rule after rule. In Org, a radio target <<<NUMBER>>> stays visible, and every mention of “NUMBER” elsewhere becomes a link to it, sans brackets. In a graph, the radio target is a node, and every item mentioning it —in whatever case— has an arc to it:

﴾What You Write﴿ 
#+begin_graph
+ <<<NUMBER>>>, a run of digits
+ <<<PLUS>>>, the + sign
+ factor → NUMBER
+ expr → factor PLUS factor
+ a lone number, too
#+end_graph
﴾What You Get﴿

The mention stays in the label, and the radio target's own item never arcs to itself. Mind that this is Org's semantics exactly: a casual “number”, as in the last item, draws an arc too.

4. Ids and labels

Links make us name things, and a name wants to be short where a label wants to be clear. So every node has an id, which arcs and links name, and a label, which is drawn. By default both are the item's text, so these three items, spelling it out more and more, all declare one and the same node:

﴾What You Write﴿ 
#+begin_graph
+ expr

+ <<expr>> expr

+ <<expr>> expr
  | label | expr |
#+end_graph
﴾What You Get﴿

When the two should differ, we set either one apart: a <<target>> gives the id, and a | label | row gives the label:

﴾What You Write﴿ 
#+begin_graph
+ <<expr>> Expression
  + <<term>> Term
    + factor
      | label | Factor: a number, or ( expr ) |
      + [[expr]]
+ Sum
  + [[term]]
#+end_graph
﴾What You Get﴿
  • The id is the <<target>>, else the text —sans markup, links, footnotes, and tags.
  • The label is the label row, else the text; markup makes it an HTML-like one.
  • Two items with one id are one node, so an item may appear twice to gain more children.

5. Styling: one key-value syntax

Out of the box, Graphviz draws black ellipses; soon we want our tokens boxed and our rules round. Graphviz's attributes are key-value pairs, and Org's key-value syntax is the two-column table. So a table beneath an item styles that item: one syntax, from a single node up to the whole graph.

5.1. A node's table, and two kinds of keys

In a parse tree, the leaves are tokens, straight from the lexer; we box them, so they read apart from the grammar's rules:

﴾What You Write﴿ 
#+begin_graph
+ term
  + factor
    + <<one>> NUMBER 1
      | shape | box   |
  + STAR
    | shape | box |
    | label | *   |
  + factor
    + NUMBER 2
      | shape | box |
#+end_graph
﴾What You Get﴿

A plain key, such as shape, is a Graphviz attribute of the node, passed straight through. We quote its value for you, so NUMBER 1, #00ff00, and x -> y all need no quotes; already-quoted values, and <…> HTML labels, are left alone.

A key prefixed :edge. is an attribute of an arc rather than the node; a leading colon is never a Graphviz attribute, so the two kinds cannot clash. Each is met in due time:

Key Meaning
:edge.KEY attribute KEY of the arc from the parent
:edge[T].KEY attribute KEY of this item's arc to T

Any other key —a misspelt colour, or :edge.colour— makes the table a record, so the typo shows in the picture, rather than silently vanishing.

5.2. An arc's table: :edge.KEY

An arc is drawn from parent to child, so the child's table is where it is styled: an :edge.KEY row there is attribute KEY of the arc into the item. Every attribute is its own row, exactly like a node's. Peeking consumes nothing, so its arc should look tentative:

﴾What You Write﴿ 
#+begin_graph :direction right
+ parser
  + consumes :: token stream
    | :edge.penwidth | 2 |
  + /peeks at/ :: token stream
    | :edge.style | dashed |
    | :edge.color | gray   |
#+end_graph
﴾What You Get﴿

A reference is styled just the same; this is why an inline link graduates to one. The recursion back to expr is the arc that makes our grammar interesting, so we paint it:

﴾What You Write﴿ 
#+begin_graph
+ <<expr>> expression
  + term
    + factor
      + number
      + in parentheses :: [[expr]]
        | :edge.color     | red |
        | :edge.fontcolor | red |
#+end_graph
﴾What You Get﴿
  • A parallel arc is simply a second child, styled on its own; a KEY given twice is an error.
  • As in Org, an item's tables and directives may also follow its sub-items; they still belong to it.

5.3. The whole graph: the #+begingraph line

Small graphs deserve no preamble at all. So the header line takes the graph's title and any graph attribute; a parse tree laid out left to right, every node boxed, every arc grey:

﴾What You Write﴿ 
#+begin_graph How 1 * 2 + 3 - 4 parses :direction right :node.shape box :edge.color grey
+ -
  + +
    + *
      + 1
      + 2
    + 3
  + 4
#+end_graph
﴾What You Get﴿
  • The title, the words before the first :key, is the graph's label. Every graph is directed; a #+edge: :undirected: line makes all its arcs arrowless, an undirected graph.
  • :direction says which way arcs flow: down, the default, up, right, or left. It is Graphviz's rankdir ---TB, BT, LR, RL— spelled to be read; the header has no :rankdir, while #+graph: rankdir=LR keeps Graphviz's spelling.
  • :KEY V is a graph attribute; :node.KEY V and :edge.KEY V are node and edge defaults —the same KEY, node.KEY, edge.KEY spelling as table rows.
  • As on Org's own #+attr_html: lines, values need no quotes: :bgcolor #6c7086, :fontname Helvetica,Arial. A value with spaces does: :fontname "Helvetica Neue".
  • :file, :direction, :theme, :wrap, :notes, :unflatten, :unknown-tags, and :C-c_C-c belong to the block itself, never to Graphviz; each is met below. So do the Babel habits :exports and :results, which the block ignores; and :demo, which every block of this package understands.

5.4. When the preamble outgrows the line

A real graph's settings outgrow one line. Then #+graph:, #+node:, and #+edge: name what the table below them styles —the graph, every node, every arc— and they override the header. A drawer of any name, :SETTINGS: or :PALETTE:, folds them away with TAB, along with #+name: lines:

﴾What You Write﴿ 
#+begin_graph A compiler's front end
:SETTINGS:
#+graph:
| rankdir  | LR        |
| fontname | Helvetica |
#+node:
| shape    | box       |
| style    | rounded   |
| fontname | Helvetica |
#+edge:
| fontsize | 10   |
| color    | gray |
:END:
+ characters
  + lexer :: tokens
    + parser :: syntax tree
#+end_graph
﴾What You Get﴿

A short table may instead be written on its keyword's line, as Graphviz's own edge [fontsize=10 color=gray] writes it: KEY=VALUE pairs, a value with spaces in double quotes, beside any :tags:. The :SETTINGS: above is then three lines: 

#+graph: rankdir=LR fontname=Helvetica
#+node: shape=box style=rounded fontname=Helvetica
#+edge: fontsize=10 color=gray

Anything else on such a line is an error, rather than silently ignored. In Emacs, the keyword stands out, and so does each key that means something on its line —a graph's attribute on #+graph:, a node's on #+node:, an arc's on #+edge:, any on #+name:. A key left plain is one Graphviz does not know there, so a mistake shows before we export: a typo, as colour=red, or a misplaced key, as shape=box on an #+edge: line.

5.5. Subtrees inherit #+node: and #+edge:

Sometimes a style belongs to one branch, not the whole graph. A compiler folds constants: 1 * 2 is known before the program runs, so its whole subtree collapses to 2. We want that subtree shaded. Org's properties are inherited: a :PROPERTIES: drawer on a heading reaches its subheadings. So it is with an item's #+node: and #+edge: tables: they style every node and arc beneath the item, while the item itself keeps its own | key | value | rows:

﴾What You Write﴿ 
#+begin_graph Constant folding
+ -
  + +
    + *
      | xlabel | folds to 2 |
      #+node:
      | fillcolor | lightgrey |
      #+edge:
      | style | dotted |
      + 1
      + 2
    + 3
  + 4
#+end_graph
﴾What You Get﴿

Above, * keeps its plain look —only what lies beneath it is shaded— just as a heading's own properties drawer is not one of its subheadings'. Graphviz scopes such defaults by an anonymous subgraph, which draws no box. A deeper item's tables override a shallower one's, as nested :PROPERTIES: do; a node first declared elsewhere keeps the defaults of where it was declared.

5.6. Themes: a look for every graph

Every graph wears a theme, beneath all its own attributes: by default creamsicle, after D2's theme 101, Orange Creamsicle —cream boxes, orange containers lightening as they nest, dark brown lines, and italic arc labels. :theme NAME picks another of org-graph-themes, and :theme nil wears Graphviz's own look:

﴾What You Write﴿ 
#+begin_graph :theme nil
+ Org
  + exports to :: HTML
#+end_graph
﴾What You Get﴿

A theme is data, #+graph:, #+node:, and #+edge: lines' pairs, plus a fill per depth of node and of container; so a new one is a push away, and a new default a setq: 

(push '(ink :node "shape=box fontname=Helvetica" :edge "color=gray30" :container-colors "#eeeeee #ffffff")
      org-graph-themes)
(setq org-graph-theme 'ink)

6. Saying it once: templates

A parse tree repeats itself: every token the same box, every rule the same ellipse. Restating those rows at each leaf is how styles drift apart. So we name them once: a #+name: table is a reusable bundle of rows, and a tag applies it. On a headline, :work:urgent: classifies the entry; on an item, tags classify the node:

﴾What You Write﴿ 
#+begin_graph
#+name: token
| shape     | box       |
| fillcolor | lightblue |
#+name: rule
| style | bold |

+ expr :rule:
  + term :rule:
    + NUMBER 1 :token:
    + STAR :token:
      | label | * |
    + NUMBER 2 :token:
  + PLUS :token:
    | fillcolor | pink |
  + NUMBER 3 :token:
#+end_graph
﴾What You Get﴿

A short template fits on its name's line, as KEY=VALUE pairs —as #+edge: lines take them— so the two above are, tersely, #+name: token shape=box fillcolor=lightblue and #+name: rule style=bold. Several such lines in a row are several templates, and a table below one adds rows to it. In Emacs, each template of a graph —its name's line, and the table below it— wears a background of its own, from org-graph-template-backgrounds, so where one ends and the next begins shows at a glance.

Explicit rows win over a template's, so PLUS above is pink. A line may carry several tags, :token:rule:, each a template, the earlier winning on a clash —save colors: when the tags' templates color it differently, a node shows every color as stripes, tinted, or wedges if it is round, and an arc as parallel lines; a node's own fillcolor or style turns the stripes off. The same rule reaches every other line a template could apply to; in a link's description, or a description term, a tag styles the arc:

Line What its tags style
+ NUMBER 1 :token: the node
+ [[expr][:recursion:]] the arc to the reference; so too a link's mid-text
+ reduces :rule-arc: :: expr :rule: the arc, by the description term's tags; the node, by its own
#+node: :token: every node; likewise #+edge: and #+graph:
#+name: keyword :token: the template keyword, which inherits token
﴾What You Write﴿ 
#+begin_graph
#+name: recursion
| color | red    |
| style | dashed |
#+name: keyword
| fontname | Courier |
#+node: :keyword:

+ <<expr>> expression
  + term
    + factor

A label is more than a name: we want a rule in bold, a token in monospace, a formula, a second line. Again, Org already has the syntax.

9. Layout: ranks, boxes, and records

Graphviz lays out the graph for us, and mostly well; but sometimes the layout says something the graph does not mean. Here is how we take the wheel back.

9.1. Side by side: ordered lists and :@X: tags

Look again at our parse tree: 1 * 2 + 3 - 4 subtracts 4 from the rest, never the other way around, yet nothing in an unordered list promises Graphviz will draw 4 on the right. Org's + - * bullets say “these things”; 1. 2. 3. say “first, second, third”. So ordered children sit side by side, on one rank, in the order written —Graphviz no longer reshuffles them to save a crossing:

﴾What You Write﴿ 
#+begin_graph
+ -
  1. +
     1. *
        1. 1
        2. 2
     2. 3
  2. 4
#+end_graph
﴾What You Get﴿
  • An ordered top-level list, or one inside a container, shares a rank too; a lone ordered child gets no rank at all.

Nodes with no common parent share a rank when each wears a tag naming their group, :@X:, as Org's @home tags name a context. Every token is a leaf, so we line them all up, as the lexer emitted them:

﴾What You Write﴿ 
#+begin_graph
+ -
  + +
    + *
      + 1 :@tokens:
      + 2 :@tokens:
    + 3 :@tokens:
  + 4 :@tokens:
#+end_graph
﴾What You Get﴿

Two group names are reserved: :@start: sets its nodes on the first rank, Graphviz's rank=min, and :@end: on the last, rank=max —the top and bottom rows, or, under :direction right, the left and right columns. A legend's samples, say, may all sit beneath the graph, :@end:.

  • An @ tag aligns a node; it names no template, so #+name: @X is an error, as is an @ tag on an arc or a container.
  • A group's name is a label, not a position: :@2: need not sit below :@1:.
  • A group reaching into a box sets newrank=true; else Graphviz would pull its nodes out of the box.

Under splines=curved, Graphviz drops the label of an arc between two nodes on one rank; so there, such an arc's label becomes an xlabel, which it still draws.

9.2. Containers draw boxes

Some nodes belong together —a compiler's front end, say— and a box around them says so. An item tagged :container: is such a box: its children are its members, inside it, rather than the targets of its arcs. Indentation says what is in the box, as D2's braces do, and an item folds with TAB, as ever. Its table styles the box, and its #+node: and #+edge: set defaults within it:

﴾What You Write﴿ 
#+begin_graph :direction right
+ compiler

    | bgcolor | lightgrey |
    #+node: shape=box
    + lexer
      + parser
        + :container:
          + syntax tree
          + symbol table
  + Back end :container:
    | style | dashed |
    + code generator
#+end_graph
﴾What You Get﴿
  • A container is a child of its parent: above, compiler has an arc to Front end. An arc to or from a container lands on its first member, clipped at its border.
  • A reference among its children is an arc from the box, rather than a member; by way of example, + uses :: [[T]].
  • A box holds only the nodes declared within it: a member's reference to a node elsewhere draws the arc without pulling that node inside, though Graphviz would draw a node in the first box mentioning it.
  • An item of tags alone, + :container:, is an untitled box, with no label and no name to draw arcs to.
  • A container is a Graphviz cluster; | shape | cluster | is the same thing, spelled as a row.

Some nodes have insides: an AST node has a left operand, an operator, and a right operand, and each arc should leave from its own field. A record is a node drawn as a table, and Org already has tables: an item's table is its label, laid out exactly as written —unless it is the | key | value | rows of a node's table. A cell's <<target>> is its port, a cell's [[link]] is an arc from that port, and an arc reaches a port by record::port —just as Org's [[file:notes.org::target]] reaches into a file:

10. Diagrams we draw: sequences, classes, states, entities, mindmaps

Many diagrams are graphs in disguise; they differ only in how their nodes and arcs look. So rather than a syntax per kind, every graph has a few templates already, defined by org-defgraph-tag; a tag applies one, as with any #+name: template of our own, and our own of the same name wins. In Emacs, such a tag wears a face of its own, org-graph-builtin-tag, and clicking it says what it does.

org-defgraph-tag is defvar-like, a value with its docstring, yet setq-like, since evaluating it anew redefines the tag; so our own tags, used across documents, live in our init file:

  "Marks what needs attention now: red, and bold.")

13. Comforts while editing

Graphviz has 177 attributes, and nobody remembers them. So the block helps as we type, wherever we type.

  1. C-M-i (completion-at-point) and eldoc know about graph keys —in any Org buffer's graph blocks, and in the org-graph-edit-mode buffer that C-c ' opens on one, as for a source block:
    • In a key cell, completion offers the attributes valid there, plus the reserved keys; after :edge. or :edge[T]., it offers only edge attributes, prefix and all. In a value cell, it offers the values of that row's attribute, such as vee for :edge.arrowhead. Each candidate is annotated with its description.
    • On the #+begin_graph line, :r C-M-i offers :ratio and the other graph attributes, every :node.KEY and :edge.KEY, and the block's own :file, :direction, and :C-c_C-c; :direction r C-M-i then offers right.
    • Eldoc shows the description of the key on the current row, or at point on the #+begin_graph line, ending with Graphviz's default; e.g., | :edge.arrowhead | vee | shows “Style of arrowhead on the head node of an edge. Default: normal.”
  2. A directive's line validates itself as we type: #+graph:, #+node:, #+edge:, and #+name: stand out, and so does each KEY of a KEY=VALUE pair that Graphviz knows on that line. A key left plain is a typo, or a misplaced key; see When the preamble outgrows the line. Each #+name: template wears a background of its own.

  3. When we would rather pick than type, C-u RET on any table row inside a graph inserts a new | key | value | row interactively: a completion menu for the key, then one for the value —or a free-text prompt, when the attribute accepts arbitrary strings. Plain RET is unaffected. The menu shows only the attributes valid where the table sits:

    • Table under #+graph: ⟶ graph-level attributes (rankdir, splines, bgcolor, …)
    • Table under #+node: ⟶ default node attributes (shape, style, color, …)
    • Table under #+edge: ⟶ default edge attributes (arrowhead, dir, penwidth, …)
    • Table on a list item ⟶ node attributes, as above

    For a color ---bgcolor, fillcolor, fontcolor, or color— the value is picked from Helm's color list, when Helm is installed; RET inserts the color's hex code, and its name as a comment. (This replaces our old ritual of M-x helm-colors, then C-z, then C-c r.) C-u RET works in the C-c ' buffer too.

  4. Where do the descriptions come from? org-graph-attributes, which lives on its own in org-graph-attributes.el: every Graphviz attribute, scraped from Graphviz's attribute table. To add or adjust one, edit its entry there, or M-x customize-variable RET org-graph-attributes; each entry has the form: 

    (:name "shape" :valid-on (nodes) :default "ellipse"
 :values ("box" "polygon" "ellipse" …)  ;; nil → free-text prompt
 :description "Sets the shape of a node.")

    Reserved keys are described by org-graph--reserved-key-docs, and the header's own keys by org-graph--header-key-docs.

  5. When the picture is wrong, we want to see what we built. C-u C-c C-c shows the generated dot in a *org-graph dot* buffer instead of rendering a PNG, and inserts —or replaces— a #+RESULTS: holding it as a #+begin_src dot block, so the source is preserved. For a block where we always want dot, :C-c_C-c dot in its header makes plain C-c C-c show dot, and C-u C-c C-c toggles back to PNG: the prefix always flips whatever the block's default is.
  6. The image C-c C-c renders is clickable. Hovering over a node or cluster shows its tooltip —its footnotes and notes— and a click follows it: to its link's target, when its item has a web, file, or [[*Heading]] link; else to the item itself, in the #+begin_graph block. Graphviz writes an image map (-Tcmapx) beside the PNG, from the same layout, and its areas become the image's :map; it is scaled as the image is, say by org-image-actual-width. The map lives only as long as the image does: an image Org redisplays itself, say on reopening the file, is clickable again after another C-c C-c.
  7. Big graphs make big PNGs; (setq org-image-actual-width 700) keeps them on screen. In an HTML export, a graph shrinks to the page's width by itself, and a click toggles its full size.
  8. In a :demo live graph, as throughout this README, C-c C-c still renders the graph: a live demo keeps no snapshot to take.
  9. A tag is a link to its template: clicking it, or C-c C-o on it, jumps to its #+name: line —the graph's own, else one outside every graph— as a template's lookup goes. A tag every graph has, from org-defgraph-tag, says what it does instead, as eldoc does with point on it; and an undefined tag says that a template is made up for it, and that :unknown-tags error forbids that.
